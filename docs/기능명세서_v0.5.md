## 3. 화면 전이

```
홈 ─[동승 출발]→ 출발 화면(목적지 검색·최근 목적지, 인원 확인 알림, requestTrip으로 ETA·정체 선취득) ─[출발]→ 내비 안내(앱 가려짐, 주행 중 동작 없음)
                                                        │
   (나란히 배치일 때만 휴게소 정차를 기어 P·D 시각으로 자동 기록)
        도착 → ⓪ 계산 연출(매번, [건너뛰기]) → ① 노고 영수증(이 화면 안에서 "중간에 쉰 시간" 묻기, 답하면 줄 값 다시 계산) → ② 제안(A 또는 B) → 선택 → 홈
```

- **계산 연출** `[디자인]`: 도착하면 매번 약 13초 동안 계산 연출이 나와요(2D 차는 공용 세단 1종). [건너뛰기]를 누르면 바로 영수증으로 가요(명준 결정, 디자인 Q-2026-11-07-06).

- **홈** `[제안]`: [동승 출발] 버튼, 진행 중인 출발이 있으면 그 상태, 최근 기록 3건을 보여 줘요. 기록을 쌓아 보는 화면은 2차예요(PRD 10장).
- **나눠 낼 인원이 1명**이면(혼자 탄 주행) 영수증만 보여 주고 제안은 하지 않아요. PRD 열린 결정 6의 기본값이고, 디자인에서 바뀔 수 있어요.

## 4. F20 동승 출발

| 항목 | 명세 |

| 트리거 | 출발 화면에서 [출발] (기어 P) |
| 입력 | 목적지: 서버 `GET /v1/places?query=`(카카오 로컬 키워드 검색 대행)로 찾거나, `NaviHelper.getRecentDestinationInfo`의 최근 목적지에서 골라요. 지도에서 찍기는 1차 제외예요. NaviHelper에 검색 API가 있으면 그걸 우선해요 `[June 확인]`. 나눠 낼 인원 n: 착석 센서(P `CAR_SEATS`)로 감지한 뒤 **인원 확인 알림**(PR #34·#40, "3명이 탔어요 · 나눠 낼 인원을 맞춰 주세요" −/+ [확인] [닫기])을 출발 화면에서 다시 써요. 현재 위치: `NaviHelper`, 메모리에만 둬요 |
| 처리 | ① `requestRoute(목적지)` → `onRouteStarted(RouteStartInfo)`: `duration`(ETA 초), `distance`(m)를 저장해요. ② `getRouteStateInfo` → `onRouteStateInfo` → `trafficStatus.congestionItemList`: **목록이 채워진 응답**일 때 SLOW·HEAVY 구간의 `distance` 합(m)과 **구간마다 `distance ÷ avrSpeed` 합**(초)을 저장해요. `trafficCongestionTime`은 분 단위로 올린 값이라(짧은 구간도 최소 60초) 합이 약 1.75배 부풀어서 쓰지 않아요(June 실측). 첫 응답은 0개라, 재조회는 앱이 보이는 동안 최대 2회만 해요(폴링 없음). ③ `GET /v1/weather`(출발 좌표) → 강수 형태. ④ 차 트립 주행 시간이 읽히면 교차 확인용으로 저장해요(에뮬 미지원). ⑤ 출발 기록을 저장해요 |

| 받는 시점 | 기본 배치에서는 [출발] 뒤 1초 안에 순정 내비가 차곡을 덮어 `onStop`되고 약 11초 뒤 동결돼요(June #51 실측). 그래서 ①②(`onRouteStarted`·`congestionItemList`)를 받지 못해요. **출발 화면이 보이는 동안 `requestTrip`으로** ETA(`eta`), 경로 거리, **정체 비율**(SLOW·HEAVY 구간 수 × 4%)과 **정체 km**(비율 × 경로 거리)를 받아 둬요. 내비와 나란히 띄워 차곡이 살아 있으면 ②로 구간 목록도 받아 정체 '분'(구간마다 `distance ÷ avrSpeed` 합)을 써요 |
| 출력 | 내비 안내가 시작되고 앱은 가려져요 |

- AC-F20-1: [출발] 한 번에 출발 기록 1건이 생겨요. 콜백이 두 번 와도 1건이에요.
- AC-F20-2: 저장된 `congestion_*`는 구간 수가 1 이상인 응답에서 나와요. `getRouteStateInfo` 호출은 3회 이하예요.
- AC-F20-3: 날씨 서버를 내려도 출발이 진행돼요.

- `[June 확인]`: [출발] 뒤 순정 내비가 앞으로 올 때 차곡이 `onStop`되는지(위 '받는 시점'과 F21 1순위가 여기에 달려 있어요).

## 5. F21 정차 빼기 (#49·#58)

휴게소 정차가 운전 시간에 섞이면 영수증이 틀려요(점심 1시간이 "예상보다 더 +60분"이 됨). June 실측(#51, 11/7)에 따르면 기본 배치에서는 [출발] 뒤 1초 안에 순정 내비가 차곡을 덮어 `onStop`되고 약 11초 뒤 동결돼요. 그래서 주행 중 신호를 받을 수 없고, **도착 뒤 "중간에 쉰 시간"을 한 번 묻는 게 기본**이에요(#58, 명준 결정). 질문은 **영수증 화면 안**에 있고, 답하면 줄 값을 다시 계산해요(디자인 Q-2026-11-07-06). 가볍게 끝나는 팝업·칩이고, 모양은 디자인에서 정해요.

| 항목 | 명세 |
| --- | --- |
| 기본: 도착 뒤 한 번 묻기 | 영수증 화면 안에서 "중간에 쉰 시간"을 한 번 물어요: 없음 / 15분 / 30분 / 1시간 이상 → 0 / 15 / 30 / 60분. 운전 시간 T = 경과 시간 − 답. 답하기 전에는 기본 선택(자동 값이 있으면 그 값, 없으면 '없음')으로 계산한 영수증을 보여 줘요 |

**수식** (#47)

```
엔진 입력은 둘 중 하나예요(앱이 F21 결과로 채움):
  기본  쉰 시간 답 Q(0·15·30·60분)      → 주행 구간을 모름
  보조  정차 목록 [(시작, 끝), …]        → 주행 구간 = [출발, 도착] − 정차들 (나란히 배치)

경과 E       = 도착 시각 − 출발 시각(분)
T            = 기본: E − Q / 보조: 주행 구간 길이의 합
피로 구간    = 기본: Q ≥ 15이면 [T/2, T/2], 아니면 [T]
               보조: 15분 이상 정차로 나뉜 연속 주행 구간(15분 미만 정차는 이어 붙임)
정체 분 C    = 기본: 정체 비율 × T                   ※ 출발 전 requestTrip의 비율(효성 결정, 열린 결정 28)
               구간 목록이 있으면: min(congestion_s ÷ 60, T)  ※ congestion_s = Σ 구간 distance ÷ avrSpeed
지연 분 D    = max(0, T − eta_s ÷ 60), 단 D < 0.10 × (eta_s ÷ 60)이면 0
밤 분 N      = 기본: [출발, 도착]과 밤이 겹친 분 × (T ÷ E)
               보조: 주행 구간과 [일몰, 다음 일출]이 겹친 분
비·눈 분     = T의 앞 절반은 weather_dep, 뒤 절반은 weather_arr로 판정한 비 분 R, 눈 분 S
피로 F       = Σ 피로 구간마다 max(0, 구간 − 120) × 0.125
노고(분)     = T + 0.27·C + 0.27·D + 0.04·N + 0.40·R + 0.49·S + F
부담 배수    = 노고 ÷ T
줄별 가산(%) = 그 항의 가산 ÷ T × 100
```
